# CS683: Python and Java Microarchitecture Project

This project compares instruction traces from five small workloads written in
Python and Java. Intel PIN records instructions and memory addresses. ChampSim
replays each trace on a configured simulated processor. The report focuses on
cache behavior, branches, instructions per cycle (IPC), and a simulator-based
stall classification.

> **Important:** These are trace-driven simulation results. They are not
> wall-clock timings, and they do not describe every Python or Java program.
> The captured traces include language runtime instructions as well as
> workload instructions.

## Workloads and how they are implemented

The Java and Python versions use the same workload ideas, but their data
representations are not identical.

| Program | Implementation |
| --- | --- |
| `Sequential` | Creates a 65,536-element array/list and scans it 256 times, adding the values. |
| `BranchPredictable` | Runs a conditional ten million times. One outcome occurs 63 times out of 64. |
| `BranchUnpredictable` | Updates a fixed-seed, 32-bit pseudo-random state and branches on its sign/high bit. The pattern is repeatable. |
| `PointerChase` | Builds an 8,192-node cycle and follows dependent `next` references four million times. Each next address depends on the previous load. |
| `DynamicDispatch` | Selects among four operation implementations and invokes one five million times through an interface or method call. |

The code is in `programs/Java/` and `programs/Python/`. The Java programs name
their main thread `checkpoint-main`; the PIN tracer uses this name to avoid
capturing JVM background threads. Each program prints its final value so the
work is observable.

## How the experiment works

1. **Capture:** PIN records an instruction trace for a benchmark. The current
   checkpoint skips 5,000,000 instructions, then records 1,000,000.
2. **Replay:** ChampSim warms up for 100,000 instructions, then simulates about
   899,000 instructions. The final count can be a little higher because
   instructions retire in groups.
3. **Summarize:** Python scripts parse the ChampSim output and generate CSV,
   LaTeX tables, paired comparisons, and plots.
4. **Report:** `checkpoint1_report.tex` includes the generated tables and plots;
   the compiled version is `checkpoint1_report.pdf`.

The baseline ChampSim configuration is in `Champsim/champsim_config.json`. It
models one core with a bimodal branch predictor, a 48 KiB L1 data cache, a
512 KiB L2 cache, and a 2 MiB last-level cache (LLC). Cache hit latencies are
5, 10, and 20 cycles. Prefetchers are disabled.

The memory-wait and pipeline/other counters are a project addition to ChampSim.
They classify a cycle with no retiring instructions as memory-wait when the
reorder-buffer head is waiting on an issued load; other zero-retirement cycles
are classified as pipeline/other. This is a repeatable simulator rule, not a
complete attribution of real processor stalls.

## Requirements

Run the workflow in Linux or WSL. The scripts use Bash, Linux Intel PIN, and
Linux build tools, so native Windows PowerShell is not supported.

You will need:

- Git, GNU Make, a C++ compiler, and the build tools required by ChampSim.
- Python 3 and Java/JDK (the report's recorded run used Python 3.12.3 and
  OpenJDK 21).
- Intel PIN installed on the Linux/WSL system. Its version and installation
  details are described in `Champsim/tracer/pin/README.md`.
- A LaTeX installation with `latexmk` and PGFPlots if you want to rebuild the
  PDF and figures.

## Clone and build

Clone the repository with its vcpkg submodule:

```sh
git clone --recurse-submodules https://github.com/tagoreyendikatla/CS683-Project.git
cd CS683-Project
```

Install ChampSim's dependencies and build its baseline simulator:

```sh
cd Champsim
git submodule update --init --recursive
./vcpkg/bootstrap-vcpkg.sh
./vcpkg/vcpkg install
./config.sh champsim_config.json
make
cd ..
```

Set `PIN_ROOT` to the directory containing the PIN executable, then build the
project's tracer:

```sh
export PIN_ROOT="$HOME/tools/pin"
make -C Champsim/tracer/pin PIN_ROOT="$PIN_ROOT"
```

The project Makefile uses that variable to find PIN. Its default is
`$HOME/tools/pin-external-4.4-99977-g54fbb8814-gcc-linux`; override it if PIN is
installed somewhere else.

## Reproduce the baseline run

Run all five workloads in both languages with the checkpoint's recorded
settings:

```sh
make checkpoint1 \
  PIN_ROOT="$PIN_ROOT" \
  TRACE_SKIP_INSTRUCTIONS=5000000 \
  TRACE_INSTRUCTIONS=1000000 \
  WARMUP_INSTRUCTIONS=100000 \
  SIMULATION_INSTRUCTIONS=899000
```

This captures new binary traces in `traces/` and writes ChampSim output to
`results/`. Each trace is about 64 MB, so the ten full-size traces need roughly
640 MB of disk space. These files are ignored by Git.

To run a single workload instead, for example:

```sh
make PROGRAM=PointerChase run-python PIN_ROOT="$PIN_ROOT"
make PROGRAM=PointerChase run-java PIN_ROOT="$PIN_ROOT"
```

The Makefile also accepts `CHECKPOINT_LANGUAGES=python` or
`CHECKPOINT_LANGUAGES=java` to run only one language. Keep the trace length
larger than the warmup plus simulation counts and the configured margin.

## Regenerate metrics, plots, and report

After all ten baseline traces and results exist, run:

```sh
python3 analysis/summarize_checkpoint1.py \
  --trace-skip 5000000 \
  --trace-instructions 1000000 \
  --simulation-instructions 899000
```

This validates the inputs and regenerates `checkpoint1_metrics.csv`,
`checkpoint1_results.tex`, `checkpoint1_stalls.tex`,
`checkpoint1_findings.tex`, and `checkpoint1_plots.tex`.

If the cache-sensitivity output files already exist under
`results/sensitivity/`, regenerate their summary files and plot with:

```sh
python3 analysis/summarize_cache_sensitivity.py
```

Compile the report and its plots with:

```sh
latexmk -pdf checkpoint1_report.tex
```

The report uses PGFPlots for its figures. The `.tex` plot and table files are
generated from the same parsed results as the CSVs, so do not edit their
numbers by hand.

## Cache-capacity experiment

The capacity experiment compares the baseline against a four-times-larger L1D
and a four-times-larger LLC. The JSON files in `analysis/` change cache size
while keeping the configured hit latency unchanged.

Build both variants and then restore the baseline simulator:

```sh
cd Champsim
./config.sh champsim_config.json ../analysis/checkpoint1_l1d_capacity.json
make
./config.sh champsim_config.json ../analysis/checkpoint1_llc_capacity.json
make
./config.sh champsim_config.json
make
cd ..
```

The sensitivity run needs the full-size traces from the baseline step. It
copies the baseline result files, then runs the L1D and LLC variants:

```sh
bash analysis/run_checkpoint1_cache_sensitivity.sh
python3 analysis/summarize_cache_sensitivity.py
```

## Reading the results

- **IPC** is instructions completed per cycle in the simulation.
- **MPKI** is misses per thousand instructions.
- **Cache miss rate** is the number of misses divided by the number of
  accesses.
- **Memory-wait share** is the fraction of total simulated cycles classified
  as memory-wait by the project-specific rule above.
- The cache-capacity plot shows percentage cycle reduction versus baseline.
  Small or zero changes apply to these specific trace windows, not to all
  workloads or real hardware.

There is one trace window per workload in the current report, without
repeat-run variation. For stronger conclusions, use longer trace windows and
repeat the runs. Interpreter and JVM instructions are part of the trace, and
the Java application-thread trace excludes JVM background threads. Treat
workload contrasts as clues, not as proof that one source-level operation
caused a measured result.

## Main project files

- `Makefile` — captures traces, compiles Java benchmarks, and runs baseline
  simulations.
- `analysis/run_checkpoint1_simulations.sh` — replays existing baseline traces
  after rebuilding ChampSim.
- `analysis/run_checkpoint1_cache_sensitivity.sh` — runs each trace with the
  baseline, larger-L1D, and larger-LLC simulators.
- `analysis/summarize_checkpoint1.py` — validates baseline outputs and creates
  metrics, tables, comparisons, and the memory-wait plot.
- `analysis/summarize_cache_sensitivity.py` — summarizes cache variants and
  creates the cache-capacity plot.
- `programs/README.md` — short descriptions of the benchmark programs and
  their run settings.
- `Champsim/README.md` — upstream ChampSim build and simulator documentation.

See `howtopresent.pdf` for the course guidance used to shape the checkpoint
report.
